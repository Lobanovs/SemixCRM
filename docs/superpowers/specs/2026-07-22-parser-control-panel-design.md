# Рабочая панель парсера клиентов

## Цель

Сделать настройки и запуск парсера понятными и надёжными на desktop: пользователь должен сразу видеть, с какой страницы 2GIS начнётся поиск, сохранять параметры с явной обратной связью и запускать парсер только с актуальными значениями.

## Подтверждённая проблема

Текущий frontend уже отправляет `start_page` в API и backend сохраняет его корректно. Браузерная проверка подтвердила успешный PUT и отображение сохранённой страницы в карточке. Проблема находится в UX: поле стартовой страницы спрятано ниже длинного списка ниш внутри прокручиваемой модалки. На обычном desktop-экране кнопка «Сохранить настройки» видна раньше самого поля, а вложенная прокрутка списка ниш маскирует внешнюю прокрутку формы.

## Выбранный подход

Основные параметры переносятся из общей модалки непосредственно в карточку «Парсер клиентов»:

- город;
- источники;
- стартовая страница 2GIS;
- лимит на нишу и источник;
- краткое резюме выбранных ниш.

Длинный список ниш открывается отдельным компактным диалогом. В нём нет города, источников, страницы и лимита, поэтому пользователь решает одну задачу и не сталкивается с двумя прокручиваемыми областями.

## Компоненты

### `ParserControlPanel`

Desktop-панель в существующей правой колонке. Она получает текущий draft настроек и обработчики изменения, сохранения и запуска. Все поля имеют видимые подписи, а кнопки `−` и `+` для страницы имеют доступные имена и размер не меньше 44 px.

Панель показывает один из четырёх статусов:

- настройки сохранены;
- есть несохранённые изменения;
- идёт сохранение;
- идёт парсинг.

### `ParserNichesDialog`

Диалог отвечает только за выбор ниш и поиск по списку. Кнопка «Применить» обновляет draft панели, но не вызывает API. Кнопка «Отмена» закрывает диалог без изменения draft.

### API-операции

Сохранение настроек выносится в одну функцию `persistParserSettings(settings)`. Она выполняет `PUT /api/parser/settings`, проверяет HTTP-ответ и возвращает нормализованные настройки backend.

Обычная кнопка «Сохранить» вызывает только эту функцию. Кнопка «Запустить парсер» сначала вызывает `persistParserSettings()` для текущего draft, обновляет сохранённое состояние ответом backend и только затем выполняет `POST /api/clients/parse`. Таким образом, запуск никогда не использует старые город, ниши, источники, лимит или `start_page`.

## Состояния и ошибки

- Пока идёт сохранение, обе action-кнопки отключены.
- Пока идёт парсинг, изменение полей и повторный запуск отключены.
- Ошибка сохранения останавливает запуск и отображается внутри панели с `role="alert"`.
- Успешное сохранение отображается рядом с действиями с `role="status"`.
- Для запуска нужны хотя бы одна ниша и один источник; ошибка показывается до сетевого запроса.
- `start_page` ограничивается диапазоном 1–999, `limit` — текущим диапазоном 1–50.

## Визуальные правила

Используется существующая дизайн-система Semix CRM: минималистичная dashboard-подача, профессиональный синий CTA, Lucide-иконки, радиус 8–12 px и видимые focus-состояния. UI/UX Pro Max рекомендует для CRM flat/minimal оформление, явные labels, submit feedback, inline errors и минимум 44 px для управляющих кнопок — эти правила обязательны для панели.

Основной целевой viewport — desktop от 1024 px. На меньшей ширине панель может переходить в одну колонку; отдельная мобильная композиция не входит в задачу, но горизонтальный overflow недопустим.

## Тестирование

1. Компонентный тест подтверждает, что поле стартовой страницы видно без открытия общей модалки.
2. Изменение страницы обновляет draft и маркирует настройки как несохранённые.
3. Сохранение отправляет `start_page` и остальные значения в PUT и показывает успешный статус.
4. Запуск сначала выполняет PUT, затем POST с ответом сохранения.
5. Ошибка PUT не допускает POST запуска и видимо отображается в панели.
6. Browser-проверка на desktop меняет страницу, сохраняет её, сверяет GET `/api/parser/settings` и проверяет запуск задачи.
7. Полный backend unittest и frontend production build остаются зелёными.

## Вне задачи

- Переработка списка и карточек клиентов.
- Полноценный отдельный mobile-дизайн.
- Изменение backend-схемы настроек.
- Исправление внешнего источника Яндекс Карт, который по-прежнему зависит от LeadHunt.
